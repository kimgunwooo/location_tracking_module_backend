## 💡 기술적 고민점
### 1. 서버의 event를 클라이언트로 보내는 방법
크게 4가지 안 중에서 고민을 했습니다.

`polling`, `long-polling`, `websocket`, `SSE`

저희 서비스의 특성 상 실시간 성이 크게 중요하지 않고, 기획 특성상 서버에서 먼저 클라이언트로 보내는 경우는 없기에, `polling` 기법으로 결정을 했습니다.

가장 쉬운 방법이라 괜히 도입하기에 고민이 많았지만, 오버 엔지니어링을 최소화하자는 마음으로 도입했습니다.

### 2. 성능 개선
가장 간단한 방법인 `polling` 의 특성상 클라이언트에서 계속적으로 reqeust를 날리기 때문에 클라이언트가 많아짐에 따라 서버의 부담이 급증할 수 있게 됩니다.
또한 http 오버헤드가 발생한다는 단점이 있습니다.

결제 기능이 포함되어있는 서비스이기 때문에 많은 요청이 들어오더라도 안정적으로 처리할 수 있는 시스템이 필요했습니다.

이처럼 성능 개선에 대한 고민들을 아래에서 하나하나 설명해보겠습니다.

#### 1) Keep-Alive
HTTP 프로토콜의 Connectionless한 특성 때문에 서버-클라이언트 연결 이후에 서버가 응답을 하면 맺었던 연결을 끊어버리는 성질을 가지고 있습니다.

클라이언트의 모든 요청에 대해 매번 새로운 연결과 해제 작업을 수행해야 하고, 이로 인한 오버헤드가 발생합니다.

그렇기에 Keep-Alive 기능을 사용했습니다.

요청에 의한 응답을 완료했을 때, 연결을 바로 끊지 않고 일정 시간만큼 대기합니다.

불필요한 Handshake 과정을 줄여주기 때문에 성능 향상을 기대할 수 있습니다.

HTTP 1.1 부터 default로 제공하는 기능이기에 추가로 크게 변경할 부분은 없었지만, `polling` 에서의 단점을 이해하고 해결 방안을 모색하는 점에서 시야를 넓힐 수 있었습니다.

#### 2) 데이터 분석
우리 프로젝트의 프론트인 IOS 즉, 아이폰으로 부터 3초에 1번 간격으로 데이터(좌표) 저장 요청이 들어옵니다.
(그보다 빨리 전송해버리면 배터리 성능 대비 손해)

그리고 데이터는 위도, 경도를 포함하는 아주 작은 데이터입니다.

그래서 한 배달은 최대 20분으로 한 배달에 대해서만 쓰기 요청이 400번, 해당 데이터의 조회 요청이 400번 발생합니다.

### 개선 과정

#### 1. DB 선택
쉽게 생각해서 RDB에 저장할 수 있습니다.

하지만, 데이터를 살펴보면 짧은 시간에 많은 양의 데이터에 대해 읽기/쓰기 명령이 들어오고, 좌표 값이기 때문에 변경이 존재하지 않습니다.

그렇기에 정합성이 중요하지 않고, 입출력이 빠른 NoSQL의 Document기반 MongoDB를 사용하기로 결정했습니다.

#### 2. 공통 병목 지점 파악 & 캐시 읽기 전략
구현된 API에서 공통적으로 DB에 접근해서 정보를 받아오는 공통 병목 지점을 파악했습니다.

이를 Redis를 도입해서 캐싱하는 방안으로 개선했습니다.

먼저 Redis에서 찾아보고, 존재하지 않으면 DB에서 접근해 다시 Redis에 저장하는 `Look Aside` 패턴을 적용하였습니다.


> LocalCache 사용을 먼저 고려해 보았지만, 다른 서버와 데이터 공유가 힘들기에 각 서버에 중복된 데이터를 보관해야 해서 데이터 일관성이 깨질 수 있는 단점이 있었습니다.

#### 3. 캐시 쓰기 전략
먼저 쓰기 요청이 들어왔을 때, Redis와 DB에 둘 다 저장하는 `Write Through` 패턴을 적용했습니다.
그렇기에 읽기 

하지만, 이 방법으로 성능 테스트를 진행해 봤을 때는 MongoDB 의 부하가 급격하게 증가하는 문제가 있었습니다.

그렇기에 `Write Back` 패턴을 적용했습니다.

이는 Redis에 모두 쓰고, 일정 시점이 되었을 때 DB로 벌크성으로 저장하는 방식입니다.

최종적으로 읽기/쓰기 요청 전부 Redis 를 통하게 하고, 종룟 시점에 비동기적으로 Redis -> DB 로의 벌크성 저장을 함으로써 확연한 개선을 확인할 수 있었습니다.

> 비동기 처리시에 문제가 생긴다면, 반환을 해줄 수 없기에 실패 처리 로직이 추가로 필요했습니다. Exponential Backoff + Jitter 방식으로 재시도 처리 로직을 구현했고, 정해진 재시도 횟수를 넘으면 log 를 찍는 형식으로 구현했습니다.

### 성능 테스트
locust 성능 테스트 툴을 사용해서 점차 개선을 할 때마다 얼마나 개선되었는지 테스트 해 보았습니다.

각 테스트의 Setting 값을 제공하고, 결과에 따른 설명을 추가했습니다.


#### 1. MongoDB만 사용한 방식
Setting
- 사용자 수 : 1000 (ramp up 100)
- worker : 1
- time_out : 10s
- 약 4분 진행
![image](https://github.com/user-attachments/assets/739c2f1b-40f9-4207-92a6-05343dba3d02)
![image](https://github.com/user-attachments/assets/d321ee16-a09f-44a4-b49d-1dd4c83354c7)

단지 MongoDB 만 사용했을 때는 단 4분만에 들어오는 request를 처리하지 못하고, 대기 시간이 길어지며 최종적으로 요청이 실패하게 됩니다. 대부분의 사용자는 대기 시간이 3초를 넘어갔을 때 이탈률이 높아지는 것을 고려해보면 최악의 성능을 낸다고 볼 수 있습니다.

#### 2. 병목지점을 파악 후, 캐시 읽기 전략을 사용했을 때
Setting
- 사용자 수 : 1000 (ramp up 100)
- worker : 3
- 약 5분 진행

![image](https://github.com/user-attachments/assets/08376cd6-502a-4dfe-b119-f90a36c0a082)

해당 테스트부터는 worker가 1대로는 제대로된 부하를 생성하지 못해서, 3대로 테스트 하였습니다.

locust를 docker를 통해 띄움으로 써 분산 환경에서의 테스트를 진행할 수 있었습니다.

![image](https://github.com/user-attachments/assets/2942c28d-4a68-40e5-a5b4-cffa162ceac9)
![image](https://github.com/user-attachments/assets/7832ff9e-76c5-4e4b-8db6-1f5d5198680e)

그래프를 살펴보면 처음엔 약 900 RPS로 잘 처리하는가 싶었지만, 5분 후 200대 까지 줄어든 것을 확인할 수 있습니다.

여기서 살펴볼 것은 종료처리시에 추가로 1000 개의 request가 쌓이면서 해당 요청들이 모두 실패한 것을 확인할 수 있었습니다.

> 이 부분은 BlockingQueue의 최대 용량을 늘려줌으로써 해결할 수 있었습니다.

![image](https://github.com/user-attachments/assets/4fa30384-c975-4af1-9fde-8486c0775373)

추가로 확인해볼 사항은 MongoDB의 CPU 사용률이 비정상적으로 증가한 것을 확인할 수 있었습니다. 

이 문제의 발생 원인을 찾기 위한 3가지를 파악해 보았습니다.

1. 데이터의 크기
2. Slow Query
3. Non-Indexed Document

데이터의 크기는 매우 작았고, 저장은 단순 Query 그리고 조회 Query는 이미 최적화를 진행했었습니다.
index를 적용하기보다는 `Write Back` 패턴을 적용해서 Redis 를 통해 저장/조회를 거치는 식으로 해결하고자 결정했습니다.

#### 3. Write Back 패턴을 적용했을 때
Setting
- 사용자 수 : 1000 (ramp up 100)
- worker : 3
- 약 5분 진행

또한 실패한 request가 거의 없이 높은 처리량을 보여주었습니다.

## 🙋‍♂️ 느낀 점
모듈을 구현함에 있어서 개발에만 집중한다기 보다는 전략적인 부분에서도 많은 시간을 할애한 것 같습니다. <br>
처음에는 그저 토큰만 사용해서 트래킹을 하면 되지 않을까 생각했지만, 트래킹의 정보를 제공하는 기업과 받는 기업이 다를 경우 처리해주지 못하는 경우가 생겼었습니다. 이는 결제한 사용자에 대해 토큰을 custom 하게 생성할 수 있게해 적절한 권한을 가진 토큰을 제 3의 기업으로 전달함으로써 해결할 수 있었습니다.

사실 이때까지 프로젝트에서는 기능 구현에 중심을 맞춰서 개발을 했기에 성능 개선에 대한 부분은 고려해주지 못했었습니다. <br>
이번 프로젝트에서는 각자 맡은 기능에만 집중 할 수 있었고, 그로 인해 성능 개선과 그에 따른 성능 테스트 또한 진행할 수 있었습니다. <br>
MongoDB 집계 쿼리 최적화 부터 Redis 캐싱 전략을 하나하나 적용해보며 저희 프로젝트에선 어떤 전략이 가장 이상적인지 확인해볼 수 있었습니다. <br>
